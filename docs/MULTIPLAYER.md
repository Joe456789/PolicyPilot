# 連線對戰架構規劃(初賽後實作)

目標:2~4 位真人在同一個棋盤上同時玩,可以混入電腦對手。**初賽(11/6)前不實作**,這份文件是為了現在的設計不要擋住以後。

## 為什麼現在的程式適合改成連線

- 遊戲規則(`src/game/*`)是**純函式、確定性**:`run(state, fn)` 複製狀態並用種子亂數,同一個種子與同一串動作一定得到同一個結果。
- 玩家之間的互動已經集中在一個地方:`pendingOps`(過路費、拍賣)由 `match.js` 的 `applyOps` 處理。
- 地產所有權是從每個玩家的 `props` 推導出來的(`worldOf`),不需要另外維護全域狀態。

所以連線版可以**不重寫規則**,只要把「誰在什麼時候做動作」交給伺服器仲裁。

## 建議做法:伺服器權威 + WebSocket

```
瀏覽器 A ─┐
瀏覽器 B ─┼─ WebSocket ─ Cloud Run (Node, ws) ─ 房間狀態(記憶體)
瀏覽器 C ─┘                       │
                                  └─ 規則引擎(同一份 src/game)
```

1. **房間**:`POST /api/rooms` 建立,回傳 4 碼房號;玩家用房號加入。房主按開始。
2. **伺服器保存完整對局狀態**(`players[]`,每人一個 `state`)與房間種子;所有規則在伺服器執行(防作弊,也避免各端結果不同)。
3. **回合制輪流**:輪到誰,伺服器只接受那個人的動作(`roll`、`choose`、`propAction`、`setCoverage`…),其他人只能看。
4. **同步**:每次動作後,伺服器廣播「視圖」(各玩家公開資訊:位置、淨資產、持有地產、排名、剛發生的事件),**不廣播對手的私人細節**(例如手牌、現金可以只給總額)。
5. **斷線**:30 秒沒回應就由電腦對手(`botPlan` / `botAct`)代打,重新連上即可接手。
6. **AI**:仍然由伺服器端呼叫 Gemini(金鑰只在伺服器),房間共用一份 AI 額度。

## 需要新增的東西

| 項目 | 說明 | 預估 |
|---|---|---|
| `server/rooms.js` | 房間、加入、輪流、逾時代打 | 1.5 天 |
| WebSocket 通道 | `ws` 套件,訊息格式:`{type, ...}`;重連 token | 0.5 天 |
| 前端 `net.js` | 取代 `App.jsx` 裡直接呼叫引擎的地方,改成送動作、收視圖 | 1.5 天 |
| 大廳畫面 | 建立 / 加入房間、顯示成員、開始 | 0.5 天 |
| 測試 | 兩個瀏覽器同房對戰、斷線重連、逾時代打 | 1 天 |

合計約 **5 天**。

## 要先決定的事

1. **同步還是非同步**:同步(大家同時在線,輪流)最簡單;非同步(像 Words With Friends)需要資料庫,不建議第一版做。
2. **Cloud Run 的連線限制**:WebSocket 可用,但實例要設定 `--session-affinity` 與較長的請求逾時(預設 5 分鐘,最長 60 分鐘),房間狀態放記憶體,實例重啟就會消失(可接受,第一版不做持久化)。
3. **帳號**:第一版不做登入,用暱稱 + 房號;戰績仍存各自瀏覽器。
4. **人生長度**:連線建議固定「短局」(約 12 年),避免等太久。
5. **每回合時間限制**:建議 45 秒,超時由電腦代打。
